# Play Console registration and launch

The Android code and signing candidate can be prepared before an account exists. A production launch cannot be completed before owner registration, declarations, product configuration, testing and Google review.

1. Open [Google Play Console](https://play.google.com/console/signup) using the Google account that should own the business. Choose a personal account if operating as an individual, or organization only if it matches your legal organization. The [registration guide](https://support.google.com/googleplay/android-developer/answer/6112435) describes Google's one-time US$25 fee and owner verification. Complete payment, identity, contact and device-verification requirements yourself; no account has been created or charged by this project.
2. Set the public developer name and a support email you can actively monitor. Create the app **My Health**, default language English, category Health & Fitness, initial download **Free**, and acknowledge its in-app purchases. Register/verify the package `com.peter.myhealth` as directed by Console.
3. Enroll in Play App Signing. Keep the upload key private. Use the signed Android App Bundle, not the debug APK. Google signs installed production APKs with the app-signing key. The owner's currently installed debug app uses a different signing certificate: export its JSON backup before eventually replacing it with a Play-installed release. Do not uninstall it during development.
4. Publish `privacy-policy.template.md` after filling all placeholders. Use a publicly accessible, non-geofenced HTTPS page with no login. Set `PRIVACY_POLICY_URL`, `PUBLIC_DEVELOPER_NAME` and `SUPPORT_EMAIL` in your release environment.
5. Create one-time product **`my_health_pro`**, a non-consumable purchase option. Set its local prices, countries and availability in Console; there is no hardcoded app price. Copy the app's public licensing key into `PLAY_BILLING_PUBLIC_KEY`. This is a public verification key, not your private upload key. Build a configured release with `scripts/build-release.ps1 -Submission`.
6. Complete Data safety, Health apps, Health Connect access purposes, foreground-service declarations, content rating, target audience and app-access instructions. See the companion data-safety draft. State **No ads**, optional one-time Pro purchases, and the external-device requirements for vital signs. Public builds do not require login. App lock is off by default, so review does not require the owner's biometric.
7. Use an internal test track and license testers for purchases. Verify purchase, cancellation, pending payment, acknowledgment, restore after reinstall, offline access, and revocation/refund on reconnect. Purchases cannot be meaningfully validated before a Console product and test track exist. Do not charge real customers as a substitute for license testing.
8. Test cold starts, activity-permission denial/revocation, reboot, package updates, midnight, daylight saving, battery restrictions, step history, GPS, camera denial and data restore on multiple supported Android versions/devices. Run Play's pre-launch report. Native tests in this repository and the owner's phone checks are evidence, not a substitute for this matrix.
9. New personal accounts created after November 13, 2023 generally need at least **12 opted-in testers continuously for 14 days**, then an application for production access. Check your own Console because requirements can change. [Google's testing requirements](https://support.google.com/googleplay/android-developer/answer/14151465).
10. Review the actual listing, screenshots, policy and localized prices, then submit the production release for Google review. Approval, visibility, payments-profile eligibility and earnings depend on Google and your account setup; they are not guaranteed by a successful local build.

## Private signing files

`.release/upload-key.p12` is the upload key. `.release/password.dpapi` holds its password encrypted for the current Windows account. `.release/signing.properties` contains its alias/path only. All are excluded from Git. Back up the key **and** export its password to a secure vault using `scripts/export-upload-password.ps1 -Destination <secure-file>`; the DPAPI file alone cannot be decrypted by another Windows user or a new installation without the original account's encryption keys.

`powershell -NoProfile -ExecutionPolicy Bypass -File scripts/build-release.ps1` builds a signed candidate. `-Submission` rejects missing public policy, support/developer details and billing key. It does not claim Google approval or check account-side test completion.
